# AI Feature Spec: JWT Authentication

## 1. Feature Overview

**Description:** Add JWT (JSON Web Token) authentication to the KeystoneJS API to enable stateless, token-based auth for external clients (e.g., the `app` frontend). This replaces the default cookie-based session strategy with a dual approach: cookies remain for the Admin UI, while a new REST endpoint issues JWTs for programmatic/SPA access.
**Business Value:** The `app` frontend needs a portable, stateless auth mechanism that works across origins without cookie management. JWTs are the industry standard for SPA-to-API authentication and enable future mobile client support.

## 2. Current System State (Crucial)

- Existing Infrastructure: The API is a KeystoneJS 6 app (`@keystone-6/core ^6.0.0`) using `@keystone-6/auth ^8.0.0` with PostgreSQL. It runs on port `3002`.
- Existing Auth: Cookie-based stateless sessions via `statelessSessions` in `api/auth.ts`. The `createAuth` config uses `User.email` as `identityField` and `User.password` as `secretField`. Session data includes `isAdmin`.
- Database State: The `User` model already has `id` (uuid), `name`, `email` (unique), `password` (hashed), `createdAt`, and `isAdmin` fields. No `refreshToken` column exists yet.
- Environment Variables: `.env` has `APP_PORT`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`. No `SESSION_SECRET` is currently set in `.env` (but is referenced in code). No JWT-specific secrets exist.
- Existing GraphQL Mutations: `authenticateUserWithPassword` already exists (auto-generated by `@keystone-6/auth`) and returns a `sessionToken` (cookie-based).

## 4. Interfaces & Data Contracts

- `POST /api/auth/login` Request:
  ```json
  { "email": "string", "password": "string" }
  ```

- `POST /api/auth/login` Response (200):
  ```json
  {
    "accessToken": "string (JWT)",
    "refreshToken": "string (opaque)",
    "user": {
      "id": "string (uuid)",
      "name": "string",
      "email": "string",
      "isAdmin": "boolean"
    }
  }
  ```

- `POST /api/auth/login` Response (401):
  ```json
  { "error": "Invalid email or password" }
  ```

- `POST /api/auth/refresh` Request:
  ```json
  { "refreshToken": "string" }
  ```

- `POST /api/auth/refresh` Response (200):
  ```json
  { "accessToken": "string (JWT)" }
  ```

- `POST /api/auth/refresh` Response (401):
  ```json
  { "error": "Invalid or expired refresh token" }
  ```

- `POST /api/auth/logout` Request:
  ```json
  { "refreshToken": "string" }
  ```

- `POST /api/auth/logout` Response (200):
  ```json
  { "success": true }
  ```

- JWT Access Token Payload:
  ```typescript
  interface JwtPayload {
    sub: string       // User.id (uuid)
    email: string     // User.email
    isAdmin: boolean  // User.isAdmin
    iat: number       // issued at
    exp: number       // expiration (15 minutes)
  }
  ```

- Updated User Schema Field:
  ```typescript
  refreshToken: text({
    ui: { itemView: { fieldMode: 'hidden' }, listView: { fieldMode: 'hidden' }, createView: { fieldMode: 'hidden' } },
    db: { isNullable: true },
  })
  ```

## 7. Implementation Steps

1. Step 1: Checkout the new branch `feature/jwt-auth` from `dev`.
2. Step 2: Install dependencies — `npm install jsonwebtoken` and `npm install -D @types/jsonwebtoken`.
3. Step 3: Add `JWT_SECRET` and `JWT_REFRESH_SECRET` to `api/.env` (generate secure random values) and update `api/.env.example`.
4. Step 4: Add the `refreshToken` text field to the `User` list in `api/schema.ts`. Hide it from the Admin UI entirely.
5. Step 5: Create `api/lib/jwt.ts` with helper functions:
   - `generateAccessToken(user)` — signs a JWT with 15-minute expiry using `JWT_SECRET`.
   - `generateRefreshToken()` — generates a random opaque token string.
   - `verifyAccessToken(token)` — verifies and decodes a JWT.
   - `hashToken(token)` — hashes a refresh token with SHA-256 before storing.
6. Step 6: Create `api/routes/auth.ts` with an Express router:
   - `POST /api/auth/login` — validates credentials via `context.sudo().query.User.findMany`, verifies password with `@keystone-6/auth`'s identity matching, generates tokens, stores hashed refresh token on user, returns both tokens + user data.
   - `POST /api/auth/refresh` — looks up user by hashed refresh token, verifies match, issues new access token.
   - `POST /api/auth/logout` — clears the refresh token on the user record.
7. Step 7: Create `api/lib/auth-middleware.ts` — Express middleware that reads `Authorization: Bearer <token>`, calls `verifyAccessToken`, and injects the decoded payload into `req` for downstream Keystone context resolution.
8. Step 8: Modify `api/keystone.ts` — add `server.extendExpressApp` to:
   - Mount the JWT auth middleware globally (skip for Admin UI paths and auth routes).
   - Mount the auth router at `/api/auth`.
9. Step 9: Run `keystone dev` to trigger Prisma migration for the new `refreshToken` field. Verify the schema compiles and the migration applies.
10. Step 10: Manually test all three endpoints using `curl` or a REST client and commit.

## 8. Error Handling & Edge Cases

- If the `Authorization` header is missing or malformed: Allow the request to proceed without a session (anonymous access). Do not return 401 — let list-level access control handle authorization.
- If the JWT is expired: Return `401 { "error": "Token expired" }`.
- If the JWT signature is invalid: Return `401 { "error": "Invalid token" }`.
- If login credentials are wrong: Return `401 { "error": "Invalid email or password" }`. Do not distinguish between "user not found" and "wrong password" to prevent user enumeration.
- If refresh token is not found or doesn't match any user: Return `401 { "error": "Invalid or expired refresh token" }`.
- If `JWT_SECRET` or `JWT_REFRESH_SECRET` is not set: Throw a startup error immediately with a clear message, preventing the server from running in an insecure state.
- If the User associated with a valid JWT has been deleted: Middleware should fail gracefully (treat as unauthenticated).
