# Implementation Plan: Media Storage — native `image()` field revision

## Context

The first iteration of this feature (see git history on `feature/media-storage`) built a fully custom `Media` list (`filename`/`mimeType`/`size`/`driver` select/`storageKey`/`url`/`width`/`height`) plus a hand-rolled storage driver abstraction (`api/lib/storage/{local,s3,gcs}.ts`) and REST routes (`api/routes/media.ts`). Two problems surfaced in real use:

1. `driver` was a manually-typed required `select` field in Keystone's Admin UI — even though the REST route already auto-set it server-side, creating a record through the Admin UI meant picking `local`/`s3`/`gcs` by hand every time.
2. `width`/`height` were never actually computed anywhere (confirmed absent from the REST route's `data` object, so always `null`), and every field was a plain scalar with no real upload widget behind it in the Admin UI.

Investigating Keystone 6's native `image()` field turned up that it already solves both problems using code Keystone bundles internally: a real drag-and-drop upload widget in the Admin UI, and on upload it sniffs the actual file bytes (via `file-type`, restricted to `jpg`/`png`/`webp`/`gif`) and computes `width`/`height` (via `image-size`) and `filesize` automatically. The `storage` a field uses is a single named entry fixed at schema-definition time — there's no way to choose storage per-upload, which directly solves problem 1.

This plan replaces the custom architecture entirely: deletes `api/lib/storage/*`, `api/routes/media.ts`, and their test suites; rewrites the `Media` list in `api/schema.ts` around a single `image()` field; and continues on the existing `feature/media-storage` branch (not yet merged/pushed) as new commits.

**Accepted tradeoff**: Keystone's built-in `storage` config only has `kind: 'local'` and `kind: 's3'` — no native GCS support. GCS is routed through the `s3` kind's optional `endpoint` override against GCS's S3-interoperability API, using GCS **HMAC keys** (different from the service-account credentials the original custom GCS driver used). This is unverified against a live GCS bucket (no live credentials in this environment) and is documented as experimental.

## Design

- **One `image` field on `Media`** replaces the 8 old scalar fields. Keystone auto-derives `width`, `height`, `filesize`, `extension` from the actual bytes — no custom "auto-fill" code. There's intentionally no persisted original-filename column (Keystone's `image()` field doesn't have one); this is an accepted limitation, not something to work around.
- **`api/lib/media-storage.ts`** replaces the driver abstraction: a pure `resolveMediaStorage(env)` function (same fail-fast-at-import pattern as `lib/jwt.ts`) returns `{ storageConfig, activeStorageName }`. `schema.ts` uses `activeStorageName` for the `image()` field; `keystone.ts` passes `storageConfig` to `config({ storage })`. Because a field's `storage` is fixed at schema-build time, there is no per-record driver choice, ever.
  - `local`: `kind: 'local'`, `storagePath: STORAGE_LOCAL_DIR`, `generateUrl` from `STORAGE_LOCAL_PUBLIC_URL`, `serverRoute: { path: '/uploads' }` — Keystone auto-mounts this route itself, so `keystone.ts`'s manual `express.static` wiring is removed entirely.
  - `s3`: `kind: 's3'`, `bucketName`/`region`/`accessKeyId`/`secretAccessKey` from `S3_*` vars, optional `generateUrl` from `S3_PUBLIC_URL_BASE`.
  - `gcs` (experimental): `kind: 's3'` with `endpoint: 'https://storage.googleapis.com'`, `region: 'auto'`, `forcePathStyle: true`, credentials from new `GCS_HMAC_ACCESS_KEY_ID`/`GCS_HMAC_SECRET_ACCESS_KEY` vars (replacing the old service-account `GCS_PROJECT_ID`/`GCS_CLIENT_EMAIL`/`GCS_PRIVATE_KEY` vars, which no longer apply).
- **`uploadedBy` hook is unchanged**: `resolveInput.create` still force-connects `uploadedBy` to `context.session?.itemId`, ignoring client input.
- **Access control is unchanged**: same public-read / session-required-write / owner-or-admin-update-delete / soft-delete-filter shape as `Event`'s pattern — none of it was specific to the removed fields.
- **No more custom REST routes.** Uploads/deletes go through Keystone's standard `createMedia`/`updateMedia`/`deleteMedia` GraphQL mutations (multipart GraphQL upload for create, following `graphql-multipart-request-spec` — the same mechanism Keystone's own Admin UI uses under the hood). This removes the JWT-session `isAdmin`-gap workaround that lived in the custom route; the underlying gap in `api/auth.ts` still exists but is a pre-existing, already-documented limitation shared with `Event`, not something this change makes worse.
- **Dependencies shrink**: `multer`, `@types/multer`, `@aws-sdk/client-s3`, `@google-cloud/storage` are removed — Keystone already bundles `graphql-upload`, `file-type`, `image-size`, and its own S3 client internally.
- **Env vars**: drop `GCS_PROJECT_ID`/`GCS_CLIENT_EMAIL`/`GCS_PRIVATE_KEY`; add `GCS_HMAC_ACCESS_KEY_ID`/`GCS_HMAC_SECRET_ACCESS_KEY`. Keep `STORAGE_DRIVER`, `STORAGE_LOCAL_DIR`, `STORAGE_LOCAL_PUBLIC_URL`, `S3_*`, `GCS_BUCKET`, `GCS_PUBLIC_URL_BASE`.

## Steps

1. **Delete** `api/lib/storage/` (all 5 source files + 4 test files), `api/routes/media.ts`, `api/routes/media.test.ts`. Revert `api/test/mock-context.ts` to its original `dbUser`-only shape (no more `dbMedia`/settable-session additions — nothing needs them once the custom route is gone).
2. **`api/lib/media-storage.ts`** (new) — `resolveMediaStorage(env = process.env)`: reads `STORAGE_DRIVER` (default `'local'`), validates the active driver's required vars (collect *all* missing names into one thrown error), returns `{ storageConfig, activeStorageName }` per the shapes in the Design section above. Calls `dotenv.config({ path: '.env' })` at its own top (matching `lib/jwt.ts`'s pattern) — required because `schema.ts`'s import of this module executes before `keystone.ts`'s own `dotenv.config()` call runs (import statements compile to requires in source order, so relying on `keystone.ts` to load `.env` first doesn't work here). Export the module-load-time singleton `export const mediaStorage = resolveMediaStorage()`.
3. **`api/lib/media-storage.test.ts`** (new) — fabricated-env tests for each driver's happy path, default-to-local, missing-var throws (naming the var), unknown-driver throws, plus a `vi.resetModules()`/`vi.stubEnv` pair confirming the singleton throws at import time when misconfigured.
4. **`api/schema.ts`** — replace the `Media` list's `fields` with `image: image({ storage: mediaStorage.activeStorageName })`, `uploadedBy: relationship({ ref: 'User.media', many: false, ui: { itemView: { fieldMode: 'read' } } })`, `createdAt: timestamp({ defaultValue: { kind: 'now' }, ui: { createView: { fieldMode: 'hidden' }, itemView: { fieldMode: 'read' } } })`, `deletedAt: timestamp()`. Keep `access` and `hooks.resolveInput.create` as already implemented. Import `image` from `@keystone-6/core/fields` (drop the now-unused `select`/`integer` imports); import `mediaStorage` from `./lib/media-storage`. `User.media` back-relation is untouched.
5. **`api/keystone.ts`** — remove the `createMediaRouter` import/mount and the manual `/uploads` `express.static` block; add `storage: mediaStorage.storageConfig` to the top-level `config({...})`; import `mediaStorage` from `./lib/media-storage`.
6. **`api/schema.test.ts`** — keep the existing `access.operation`/`access.filter`/`resolveInput.create` tests (none were specific to the removed fields); update the hook test's fake `resolvedData` key from the old `filename` example to something field-agnostic (e.g. `image`), and cast the hook through `unknown` first if TypeScript flags the narrower test-local type as insufficiently overlapping with the real (now-stricter) generated `ResolveInputListHook` type.
7. **`api/package.json`** — remove `multer`, `@aws-sdk/client-s3`, `@google-cloud/storage` from `dependencies`; remove `@types/multer` from `devDependencies`. Run `npm uninstall` rather than hand-editing, so `package-lock.json` stays consistent.
8. **`api/.env` / `api/.env.example`** — replace the `GCS_PROJECT_ID`/`GCS_CLIENT_EMAIL`/`GCS_PRIVATE_KEY` block with `GCS_HMAC_ACCESS_KEY_ID`/`GCS_HMAC_SECRET_ACCESS_KEY`, noting the GCS section is experimental.
9. **Regenerate schema**: run `keystone dev` (or `postinstall`) against the dev Postgres container. Expect a destructive Prisma diff on the `Media` table (old scalar columns dropped, `image_id`/`image_extension`/`image_width`/`image_height`/`image_filesize` added) — acceptable, dev-only data; truncate the table first if `keystone dev`'s interactive confirmation blocks a non-interactive run.
10. **Verify** per the Verification section below, then commit.

## Verification

1. `cd api && npx tsc --noEmit` — no new type errors (the pre-existing baseline errors unrelated to this repo's own code are unaffected).
2. `cd api && npx vitest run` — all tests pass, including `routes/auth.test.ts`, `lib/jwt.test.ts`, `lib/auth-middleware.test.ts` (regression check) and the new `lib/media-storage.test.ts` + updated `schema.test.ts`.
3. Regenerate the schema (`keystone dev`) and confirm via `\d "Media"` (or equivalent) that the DB table now has `image_id`/`image_extension`/`image_width`/`image_height`/`image_filesize` columns, and that `node_modules/.keystone/types.ts` reflects the new `Media` shape.
4. Manual end-to-end smoke test: start `npm run dev`, create/log in as a test user, send a multipart GraphQL `createMedia` mutation via `curl` (see the example in the spec's Section 4 — remember the `apollo-require-preflight: true` header, required by Apollo's CSRF prevention for multipart requests), confirm the response's `width`/`height`/`filesize`/`extension` match the actual uploaded file, confirm the returned `url` serves the file byte-for-byte, confirm an anonymous `createMedia` attempt is denied, confirm `updateMedia(data: { deletedAt: ... })` removes the record from a subsequent `mediaItems` query. Clean up the test user/record afterward.
5. Per this repo's dev-server convention: kill any server process started during verification, checking the actual listening PID (`ss -ltnp | grep 3002` or `lsof -i :3002`), not just the shell wrapper that launched it.
